# P0-04 Organization catalogs

- Branch: `feat/p0-04-organization`
- Source of truth: `docs/00-analisis-inicial.md` (sections 4, 7.1, 7.2 "Operación-sitio" and "Turnos de la operación", 7.3, 8.6, phase 0 in 12.2)
- Status: in progress

## Objective

The company structure exists in the system: business units (divisions), sites and operations. An operation has exactly one site, belongs to exactly one division and has a cost center. Role scopes point at real rows through foreign keys, and a user only sees the part of the structure their scopes cover. The system still starts empty: nothing is created by migrations or code.

## Scope (authorized)

In: the new `organization` module (domain, use cases, ports, in-memory and Postgres adapters); migration `0005` with `business_units`, `sites` and `operations` (each operation carries its single site and a four-digit cost center; there is no operation-site link); real foreign keys for the non-tenant role scopes; an authorization port in the shared kernel so modules do not import each other (ADR-0005); scope-filtered reads; a minimal Spanish web page to list and create; audit of every mutation; editing an operation (name, division, site, cost center) with a mandatory reason, migration `0007` (sensitive audit action); ADR, README, AGENTS, CHANGELOG.
Out: deactivation or deletion of any of these rows, the grace-hours policy of a site (`site_grace_policy`, a later task), suppliers, asset types and equipment (`fleet`), the operation shift profile and the contracted-hours calculation that depends on it (shift profiles are deferred by the maintainer: not needed now, tracked in an issue), billing, importing the dashboard, deploy.

## Principles

- Cost: everything here costs $0 (AGENTS.md, section Cost). No service or dependency is added.
- No seed data. Test data is synthetic.
- Applied migrations are never edited; this work is migration `0005`.
- Modules never import each other. They talk through ports in the shared kernel.

## Decisions

- D1 Authorization across modules (maintainer choice, option A). The shared kernel defines a minimal `Actor` (user id, tenant id, role snapshot) and an `AccessPolicy` port: `check(actor, permission, resource) -> Result<role, error>`. `identity` implements it with the existing `authorize` and role assignments; `organization` use cases receive an actor and the port. `container.ts` wires them. The lint policy stays untouched. Recorded in ADR-0005.
- D2 Hierarchy and coverage: tenant > business unit (division) > operation; sites belong to the tenant. An operation has exactly one site (`site_id`) and a cost center; two operations may share a site. Two locations of the same client are two operations that share only the division. Resource positions: a business unit is `{tenant, businessUnit}`; a site is `{tenant, site}`; an operation is `{tenant, businessUnit, operation, site}` (it sits at every level at once). A scope covers a resource when its level id is on the resource (existing `scopeCovers`).
- D3 Role scope integrity. Migration `0005` adds nullable `scope_business_unit_id`, `scope_operation_id`, `scope_site_id` to `user_role_assignments` with composite foreign keys `(tenant_id, id)` to the new tables, a check that exactly the column matching `scope_type` is set (none for `tenant`), and a check that `scope_id` equals that column as text. The existing text `scope_id` stays, so the identity adapters and domain keep working; their insert path is extended to fill the typed column. The UI keeps offering only the `tenant` scope until a later task; the database no longer accepts a scope that points nowhere.
- D4 Reads are scope-filtered. A user sees a business unit, operation or site only if one of their active assignments with `catalog.read` covers it. A division is visible if its position `{tenant, businessUnit}` passes (an operation-scoped user does not see the parent division). An operation is visible if its position `{tenant, businessUnit, operation, site}` passes, so a division scope sees its operations, an operation scope sees itself and a site scope sees the operations at that site. A site is visible if its own position passes or any visible operation is located at it. Sibling operations stay invisible, even when they share the site. Pure domain functions decide visibility, only through the `AccessPolicy`; use cases filter with them.
- D5 Writes need `catalog.write` over the resource position (D2): creating a business unit or a site needs tenant scope; creating an operation is checked at the position `{tenant, businessUnit}` (the site and the operation id are left out on purpose), so a tenant or division scope can create and a write at site scope, or at another operation, is not enough; renaming an operation needs a scope covering its division or the operation (`{tenant, businessUnit, operation}`); editing an operation (D9) needs `catalog.write` at `{tenant, businessUnit}` of its CURRENT division and, when the division changes, also at `{tenant, businessUnit}` of the TARGET division (operation, site and operation id are left out on purpose, so operation- and site-scoped writers can rename but cannot edit or move). The division and the site must exist in the tenant (typed not found). Roles that hold `catalog.write` today: `admin` and `fleet_analyst`.
- Decision log (2026-10-18): the model of operations changed. The earlier many-to-many operation-site link (`operation_sites`, `LinkOperationSite`, `organization.link`) is gone. Reason: the maintainer clarified that each location is its own operation with its own cost center and manager, and that operations of one client share only the division. Migration `0005` and its adapters were edited in place (unmerged, applied only on ephemeral test databases and one local development database to be reset; same justification as P0-02 and P0-03).
- D6 Deferred: the operation shift profile is not part of this feature (the maintainer does not need it now); it returns as its own feature.
- D7 Names are unique per scope of ownership: business unit per tenant, operation per business unit, site per tenant, compared ignoring case AND accents. Names are stored normalized: trimmed, inner whitespace collapsed and UPPERCASE with the accents kept (`BAHÍA BLANCA`; maintainer decision of 2026-10-18). The comparison key is the normalized name with accents folded through ONE explicit map shared by TypeScript (`nameKey`) and SQL (`organization_name_key`, migration `0006`): ÁÀÂÄ->A, ÉÈÊË->E, ÍÌÎÏ->I, ÓÒÔÖ->O, ÚÙÛÜ->U; Ñ and Ç are different letters and are not folded (`NUÑEZ` and `NUNEZ` differ), so `BAHIA BLANCA` and `BAHÍA BLANCA` are the same name and the second creation is `name_taken`. The cost center is exactly four ASCII digits (a string, leading zeros matter, trimmed input accepted and stored without spaces; `invalid_cost_center` otherwise) and unique per tenant (two tenants may reuse a code). Duplicate names are a typed conflict `name_taken`, a duplicate cost center is `cost_center_taken`, never an exception, including under concurrency (the unique indexes are the safety net and `OperationRepository.add` reports which one rejected the write). Changing the cost center after creation is done through the audited edit with a mandatory reason (D9); renaming the operation stays as the quick typo fix for names.
- D8 No deletes and no deactivation in this task (privileges for the application role: SELECT, INSERT, UPDATE only; explicit `REVOKE DELETE` on the new tables because default privileges grant it, see issue #13). Mistakes are fixed by renaming (names) or by the audited edit of an operation (D9). Audit actions: `organization.business_unit.create`, `organization.operation.create` (records name, division, site and cost center in `after`), `organization.site.create`, `organization.rename`, and `organization.operation.update` (records name, division, site and cost center in `before` and `after`, plus the reason). Only `organization.operation.update` is in the sensitive-reason list (`SENSITIVE_AUDIT_ACTIONS`, trigger replaced by migration `0007`, ADR-0004).
- D9 Everything about an operation is editable after creation (maintainer decision of 2026-10-18), because there is no delete or deactivate: the division is no longer fixed. The edit sends the complete desired values (name, division, site, cost center) and a MANDATORY reason (non-blank, `hasReason`; typed `reason_required`), because moving an operation or changing its cost center changes who sees it and the accounting reconciliation. The same values as the stored ones give the typed `no_changes` without writing or auditing. Name stays unique per target division and cost center unique per tenant, both ignoring the operation itself; concurrent collisions are typed (`OperationRepository.update` returns `updated | name_taken | cost_center_taken`, Postgres runs it in a savepoint). Authorization is in D5. "Renombrar" stays as the quick typo fix for names, without a reason.

## Acceptance criteria

1. `organization` imports nothing from `identity` and lint stays green with the architecture rules unchanged.
2. A user whose only scope is one operation lists that operation and its site, and does not see another operation (even one at the same site), its division or unrelated sites; a division scope sees its operations and their sites; a site scope sees the site and the operations located at it (unit and DB tests with two synthetic tenants and several operations).
3. A role assignment whose scope points at a missing business unit, operation or site is rejected by the database; a tenant scope with a typed column set is rejected.
4. Deferred (shift profiles were removed from this feature by the maintainer).
5. Duplicate names inside the same owner return a typed conflict error; a duplicate cost center in a tenant returns `cost_center_taken`; a cost center that is not exactly four digits is rejected (check constraint and `invalid_cost_center`); an operation needs an existing site and division of its tenant.
6. Every mutation writes its audit entry in the same transaction; an audit failure rolls the change back.
7. The application role can SELECT, INSERT and UPDATE the new tables (`business_units`, `sites`, `operations`) but not DELETE or TRUNCATE.
8. The system starts empty: after migrating, the new tables have no rows.
9. `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` and `pnpm test:db` pass, locally and in CI.
