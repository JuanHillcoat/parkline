# 0013. A spare belongs to a site

- Status: Accepted
- Date: 2026-10-26
- Feature: issue-54
- Source: issue 54; migration [`0013_equipment_registration.sql`](../../db/migrations/0013_equipment_registration.sql); decisions D1 to D10 in [`odd/tasks/issue-54-equipment-registration.md`](../../odd/tasks/issue-54-equipment-registration.md); [`docs/00-analisis-inicial.md`](../00-analisis-inicial.md), section 7.2 ("Muleto como activo"); partly supersedes [ADR-0010](0010-equipment-assignments.md); builds on [ADR-0005](0005-cross-module-authorization.md), [ADR-0011](0011-equipment-image.md) and [ADR-0012](0012-meters-and-readings.md)

## Context

ADR-0010 modeled a spare ("muleto") as an assignment of kind `spare` inside an operation. Trying the application from scratch, the maintainer said: "el muleto no pertenece a ninguna operacion, por ejemplo dentro de un site puede cubrir a cualquier equipo de cualquier operacion de ese site". A spare is a reserve unit parked at a site that can cover any equipment of any operation of that site. The registration screen was also long, did not ask for the battery type nor the meter reading, and made the person choose a kind and a reason apart from the operation.

## Decision

- **The target of an assignment is an operation or a site.** An operation target is an `active` assignment (it keeps its division, operation and site). A site target is a `spare` assignment: `operation_id` and `business_unit_id` are null and `site_id` is the site. The kind is derived from the target. Checks of migration `0013`: an `active` assignment has operation and division; operation and division are both null or both set. The exclusion constraint (no overlap per equipment) is unchanged. Rows stored before this change, a spare inside an operation, stay valid and readable; no use case creates one any more, and moving or correcting such a row to its own site migrates it to the new shape.
- **Where a spare comes from.** Registering an equipment, assigning, moving and correcting accept either target (an operation to a site, a site to an operation, a site to another site). The replacement that leaves the outgoing equipment "as a muleto" now puts it at the SITE of the operation it leaves; "retire" is unchanged. The site is read through the shared-kernel port (with the same lock order as operations: division, site, operation) and an archived site is refused with `site_archived`, in every path.
- **Position and visibility.** The authorization position of a spare is `{ tenantId, siteId }`. A grant on a division or an operation never matches it, so only actors whose grants cover the whole company see and write a spare. This is a stated limitation: a supervisor or manager of an operation or a division does not see the spares of their site yet. The readings of metering (ADR-0012) use the same position.
- **Blocks.** A site with open spare assignments cannot be archived (`has_open_assignments`, through the shared-kernel `AssignmentDirectory`, which now counts them); a site with active operations is still refused first with `has_active_operations`. An archived site receives no spare.
- **Battery.** `equipments.battery_kind` (`lithium`, `lead_acid`, `combustion`) is required when registering or editing; the quantity of batteries (0 to 4) exists only for lead acid and is refused, even as 0, for the others. A database check keeps a new row from combining another kind with a quantity while old rows with no kind stay valid, readable and archivable.
- **The registration screen.** One compact dialog, fields in this order: Interno, Tipo de equipo (the word replaces "Tipo de activo" everywhere), Marca, Modelo, Serie, Año, Horómetro or Kilometraje (only when the type has a meter), Tipo de batería and, for lead acid only, Cantidad de baterías, Proveedor, Operación (every active operation and "Muleto", which asks for the Site), Fecha de ingreso, then Imagen on its own row and Observaciones last. The image is the last field so that it never moves the others when conditional fields appear; its preview is a small thumbnail beside the file input, and the grid aligns its items to the start so no field stretches. "Fecha de ingreso" is the day of the assignment AND of the first meter reading, and "Observaciones" is both the equipment's observations and the reason of the assignment (mandatory when the day is in the past, with a message that names it). The operation may stay empty: the equipment is registered unassigned. The dialog fits a 1280 x 800 screen without scrolling (a test measures the tallest case). The assign, move and correct dialogs of the detail page use the same target select.

## Consequences

- The board and the detail show a spare as "Muleto" with its site and no operation; a spare never matches an operation filter. The location card of a spare has no operation and no division.
- Deleting nothing: a spare is still an assignment with a period, a reason and an audit trail.
- What a spare covers (which equipment, from when to when) is not modeled yet: the analysis document's coverage entity is a later delivery.
- The migration is backward compatible (it relaxes two columns and adds nullable data), but the new code needs it; it must be applied to the hosted database from the maintainer machine (`pnpm db:migrate` with the owner URL) BEFORE the pull request is merged, and only with the maintainer's explicit authorization. Cost: none.
- Out of scope, tracked elsewhere: the visibility of site spares for scoped readers, Proveedores and Tipos de equipo in the sidebar with guidance when they are missing, the board with its new columns, the redesign of the detail and colors per operation.
