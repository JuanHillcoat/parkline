# 0010. Equipment assignments

- Status: Accepted
- Date: 2026-10-24
- Feature: p0-08
- Source: [`docs/00-analisis-inicial.md`](../00-analisis-inicial.md), section 7 ("Asignación con vigencia"); migration [`0010_equipment_assignments.sql`](../../db/migrations/0010_equipment_assignments.sql); decisions D1 to D10 in [`odd/tasks/p0-08-equipment-assignments.md`](../../odd/tasks/p0-08-equipment-assignments.md); builds on [ADR-0004](0004-audit-hardening.md), [ADR-0005](0005-cross-module-authorization.md), [ADR-0006](0006-organization-model.md) and [ADR-0007](0007-fleet-catalogs.md)

## Context

An equipment did not belong to any operation, so the fleet screen was only for company-wide readers (D6 of ADR-0007) and nothing recorded where an equipment had been. The maintainer needs traceability: in which operation and site each equipment was, from which day to which day; moving an equipment from one operation to another when one releases a machine that another needs; and replacing an equipment by another, where the replaced one becomes a spare ("muleto") unless the supplier withdraws it.

## Decision

- **Assignment.** `equipment_assignments` holds the equipment, the operation, the division and the site (copied from the operation when the assignment is made, so the history stays true after an operation is edited), a kind (`active` or `spare`), `valid_from` and `valid_to` as whole days with both ends inclusive (`valid_to` null means open), the reason of the latest change and who created it. Days are `YYYY-MM-DD` text everywhere; no JavaScript `Date` is used for them. Composite foreign keys keep every row inside its tenant.
- **No overlap, enforced by the database.** An equipment has at most one assignment on any day: an exclusion constraint over tenant, equipment and `daterange(valid_from, valid_to, '[]')` (it needs the `btree_gist` extension; Neon supports it on every Postgres version and it is a trusted extension, so a non-superuser database owner can install it; confirmed on a local PG 16.15 and on the hosted Neon project, where `btree_gist` 1.8 was installed by the non-superuser database owner when the migration was applied on 2026-10-24). The use cases check first to give a typed error and the constraint is the safety net: the adapter maps its violation to a typed result and rethrows anything else. Contiguous periods are valid.
- **Operations, all audited and none destructive.** Assign (first or later assignment), move (closes the open assignment the day before and opens the new one in another operation, atomically), replace, end (closes the open assignment; the equipment stays unassigned and available) and correct (changes the days, operation or kind of an existing row). Past days are allowed. Moving, replacing, ending and correcting need a reason; assigning needs one only when its start is in the past. Nothing is physically deleted and the application role has no `DELETE` on the table.
- **Replacement and the muleto-or-baja choice.** The outgoing equipment must be resolved in the same step, and there is no default that skips it: **leave it as a spare** (preselected: its assignment becomes `spare` in the same operation) or **retire it** (its assignment ends the day before and the equipment is archived with the reason; only for actors who may archive, today fleet analysts). The supplier withdrawing an equipment is a real-world fact the system cannot know, and automatically leaving a spare would hide a forgotten manual retirement. Both equipment and both audit entries change in one transaction.
- **Visibility follows the assignment (resolves D6 of ADR-0007).** An equipment is visible to an actor whose `catalog.read` covers the position of its open assignment (company, division, operation or site); an equipment with no open assignment is visible only to company-wide readers; archived equipment never has one. Suppliers and asset types stay company-wide; because a scoped reader cannot read those lists, each visible equipment carries its supplier and asset type names. A missing equipment and one the actor cannot see answer the same `not_found`, so ids cannot be probed (same pattern as issue 16). The fleet menu entry, the page and the dashboard follow it.
- **Blocks.** An equipment with an open assignment cannot be archived (`has_open_assignment`); an operation with open assignments cannot be archived (`has_open_assignments`), which `organization` learns through the shared-kernel `AssignmentDirectory` port that `fleet` implements (organization never imports fleet); an archived equipment cannot be assigned; an operation, or one whose site or division is archived, cannot receive an assignment (`operation_archived`); reopening a closed assignment in an operation archived later is refused, while correcting only the days of that history is allowed.
- **Locks.** `fleet` reads operations through the shared-kernel `OperationDirectory` port, which takes shared locks on the division, then the site, then the operation (the order the organization module uses for its parents). Every writer of one equipment (assign, archive, replace, move, end and correct) takes the equipment row `FOR NO KEY UPDATE`, after authorizing and before reading what it decides on, and a replace locks its two equipment rows in id order: without that lock two concurrent overlapping inserts deadlocked inside the exclusion check (`40P01`) instead of giving the typed overlap, and two replaces swapping the same pair could deadlock. Authorization runs before any lock so a refused actor learns nothing from contention.
- **Audit.** `fleet.assignment.move`, `fleet.assignment.replace`, `fleet.assignment.end` and `fleet.assignment.correct` are sensitive actions (they are in `SENSITIVE_AUDIT_ACTIONS` and in the trigger, 15 actions in total) and need a visible reason; `fleet.assignment.create` is not sensitive and stores its reason when given. A replace writes one `fleet.assignment.replace` entry plus the normal `fleet.archive` entry when the equipment is retired.
- **Screens.** The Equipos tab shows the columns Operación and Sitio and a state pill (Activo, Muleto, Sin asignar; archived rows keep De baja) with filters by operation and state; each equipment has a detail page `/fleet/equipment/<id>` with its information, current location, the actions the actor may use and the Historial tab. The place of the photo shows a placeholder: the image is issue 44.

## Consequences

- A scoped manager or supervisor now sees `/fleet` with the equipment of their scope; the dashboard shows them the count of the equipment they can see, never a company total.
- A move writes its reason on the row it closes as well as on the new one; the full chain of reasons is in the audit log.
- The migration adds a table, a trigger function with 15 actions and a Postgres extension. It is backward compatible (the previous code works with the new table), but the new code reads `equipment_assignments`, so it must be applied to the hosted database from the maintainer machine (`pnpm db:migrate` with the owner URL) BEFORE the pull request is merged and Vercel deploys it; otherwise the fleet screens fail until it is applied. It was applied to the hosted database on 2026-10-24, before the merge, and checked there: the extension, the exclusion constraint, the six indexes, the grants of the application role (select, insert and update only) and the trigger with the four new actions.
- Known limits: the history use case applies `catalog.read` per assignment, so a scoped reader can still read past assignments of an equipment whose current assignment is outside their scope (the detail page itself is gated by `GetEquipment`); reading an operation's site by id after authorizing the division reveals to a division writer whether that site exists, which any catalog reader could see anyway.
- Assignment at registration (issue 50): `CreateEquipment` takes an optional assignment (operation, kind, day, reason) and runs the equipment creation and the assignment in ONE transaction, through the same in-transaction function as `AssignEquipment` (`assign-in-tx.ts`), so the rules, locks and overlap check are one implementation. The create is authorized, then the assignment at that operation, before any lookup; if the assignment is refused nothing is stored. The audit holds `fleet.equipment.create` and then `fleet.assignment.create`. Without an operation the behavior is unchanged.
- Out of scope, tracked elsewhere: the equipment photo (issue 44), and hours, maintenance, repair orders, quotes, invoices and costs (issue 45).
- Cost: none; no new service or dependency.
